- **Second revision, same day: anonymity by default, robots recorded not gated, and a consent
  gate.** The author's challenge: handing out a contact with every request exposes users —
  journalists among them — to adversaries, and a template shipped worldwide should protect its
  user before it complies with anti-scraping guidance. Right on both counts, and the earlier
  reasoning had conflated two goals: the probes showed the User-Agent is *access-neutral*
  (blocks are TLS-layer), which means it is free to serve *anonymity* — a distinctive tool
  string is a cross-site tracking beacon. Cloudflare's "Agent" category had been over-read; it
  is for registered, signed vendor agents. So the fetch recipe now presents as the most common
  browser, sends no contact and no locale header, and `identity.user_agent = "declared"` is
  the opt-in for people who want to be identifiable. robots.txt (RFC 9309, the Robots
  *Exclusion* Protocol — crawler guidance) is parsed, `Crawl-delay` honoured, the verdict
  logged on every fetch, and never a gate for a single user-directed read; the host's own
  403/429/challenge is the gate, and it is respected without evasion. The reasoning, in the
  author's terms: an agent is a tool like a browser — the same requests would be made if the
  human read the page and pasted it in, at a time cost, with the same result; robots.txt is
  guidance addressed to crawlers, and a blanket `Disallow: /` read as a gate on one deliberate
  read forbids research outright. Real research has to set some guidelines aside, so the
  toolchain is transparent about what it does, respects everything it can respect without
  stopping the work — `Crawl-delay`, pacing, a host's actual answers — and leaves the rest as
  each user's explicit choice: how much to automate away and how much guidance to honour is
  set in the open, with the record kept. The largest vendors take the same position for
  user-initiated fetches, and a US appellate court has recognised it for user-directed
  agents. And a consent gate: `policy.py check` beside `graph.py check` at session start creates the policy
  skeleton, never fills a user field, and defers acquisition until the human writes a consent
  date — which also caught that the first draft had inferred the user's locale from an ASN
  lookup into `.personal-shared/README.md`; removed, left for the user.

- **The second automation label, on the author's prompt.** They recalled the old chromedriver
  binary edit that hid the controlled-browser flag (`$cdc_`). Its modern equivalent in our stack
  is `navigator.webdriver`, set by Playwright's default `--enable-automation`; the recipe now
  drops that flag and disables `AutomationControlled`, records the value the page saw, and a
  test pins that these two labels — the UA marker and the webdriver flag — are the only things
  touched. No fingerprint injection: the browser stays the browser it is. The technique is
  long-established practice — replacing `$cdc_` and `$wdc_` in the compiled WebDriver binary
  with `$abc_`, and adding `--disable-blink-features=AutomationControlled`; this recipe passes
  the same flag, and the binary edit is unnecessary because there is no WebDriver in the loop.
  The reasoning: these labels announce the driver, not the person — a real browser with a
  human at the keyboard sends neither — so removing them makes the sandbox present as the
  browser it actually is, while everything that would fabricate a *different* device stays
  off; how far to go is each user's call through `advanced_acquisition`. Verified live: a real
  news page saw `navigator.webdriver === false`, UA `Chrome/151.0.0.0`, 27 third-party requests
  refused, no profile left behind.
